# AI 智能食谱推荐系统 — PRD文档

## 1. 背景与目标

在原 ai-recipe-finder（英文版"目标驱动 meal planner"）基础上重做：

- 全面中文化
- 用更贴近真实使用习惯的"食材标签 + 口味/忌口 + 做法标签 + 自然语言饮食目标"四件套作为推荐输入，替代原来"逐行输入食材克数"的繁琐表单
- AI 输出从冷冰冰的宏量数字，改为**生活化、治愈系**的推荐文案——告诉用户"这道菜为什么适合你"
- 放弃营养量化记录（kcal/蛋白质/碳水/脂肪精确计算），改为**每周饮食回顾**：以 timetable 形式展示一周吃了什么，并由"AI 营养分析师"基于这些真实记录给出个性化反馈

## 2. 用户故事

1. 我打开 App，点几下常用食材标签（"鸡胸肉""西兰花""米饭"），不用每次都打字
2. 我选一下口味（"清淡""不吃香菜"）和做法（"快炒"）
3. 我用自己的话说一句目标："最近想增肌，多吃点蛋白质"
4. AI 给我推荐一道菜，告诉我为什么这道菜适合我现在的状态，语气温暖、鼓励
5. 我觉得不错，点"就吃这个"，系统自动记到"今天午饭"
6. 周末我打开"本周饮食回顾"，用表格看到这一周每天吃了什么，并让 AI 营养师点评我这周吃得怎么样

## 3. 核心功能模块

### 3.0 入口选择：自己做 / 点外卖（新增）

首页"今天吃什么呀"标题下方，第一步先让用户选择今天的方式：

```
[🍳 自己做]   [🛵 点外卖]
```

- 选 **自己做** → 进入 3.1~3.5 完整流程（常用食材 + 口味/忌口 + 做法 + 份量 + 目标 → AI 推荐）
- 选 **点外卖** → 进入简化流程（见 3.5a），不需要食材/做法，只需口味/忌口 + 自然语言目标，AI 从"外卖库"里按用户习惯匹配推荐
- `MealRecord` 增加 `channel: "自己做" | "外卖"` 字段，区分来源，用于本周回顾统计和 AI 营养分析师措辞（如"这周外卖比例略高"）

### 3.1 常用食材标签库
- 用户可手动输入食材名（如"鸡胸肉"），点"添加"存为常用标签
- 标签以 chip 形式平铺展示，点击即"选中/取消选中"，多选
- 支持删除自定义标签（长按或标签上的小×）
- 本次推荐请求要带上：已选中的常用标签 + 临时输入的食材（如果用户想加一个还没存过的食材）
- 存储：浏览器 localStorage，按"使用频次/最近使用"排序（可选，MVP 先按创建顺序）
- **"仅使用已有食材"开关（新增）**：默认关闭。
  - **关闭**（默认）：AI 可以在用户已选食材基础上合理补充新食材，凡是 AI 新增、用户尚未拥有的食材，会在推荐结果里单独列成"购物清单"，并在每道菜的食材清单中标注"需购买"
  - **开启**：AI 只能使用用户已选食材 + 厨房常备（盐/油/水/葱姜蒜等基础调料），不允许引入任何新食材，结果不产生购物清单
  - 这个开关解决"有时想消耗现有食材，有时家里食材不够想买点新的"两种真实场景

### 3.2 口味与备注（含标签语义表，供 AI prompt 使用）

预设标签不只是展示给用户的字面文案，每个标签都要配一句**语义说明**，写进 AI 推荐 prompt 的系统知识里，让 AI 准确理解"用户选了这个标签到底意味着什么烹饪方向"，而不是只看标签字面词猜测。

**口味标签**（多选 chip）：

| 标签 | 语义说明 | AI 推荐方向提示 |
|---|---|---|
| 清淡 | 少调味，突出食材本味 | 优先白灼/清蒸/少油少盐做法，避免重油重辣 |
| 麻辣 | 川渝风味，花椒+辣椒并重 | 可用豆瓣酱、花椒、辣椒，突出"麻"和"辣"两种感觉 |
| 微辣 | 吃辣但不嗜辣 | 辣度控制在轻微，用少量辣椒/胡椒提味而非主导 |
| 酸辣 | 酸味与辣味并重 | 可用醋、泡椒、柠檬等酸味食材搭配辣味调料 |
| 甜口 | 偏家常甜口/南方口味 | 适量加糖，或选用自带甜味的食材（南瓜、玉米、番茄） |
| 咸鲜 | 咸味为主，鲜味突出 | 可用酱油、蚝油、菌菇类提鲜 |
| 少油 | 控制烹饪用油量 | 优先蒸/煮/烤，避免煎炸 |
| 少盐 | 控制钠摄入 | 减少酱料用量，多依靠食材本味和天然香料提味 |

**忌口/过敏标签**（多选 chip）：

| 标签 | 语义说明 | AI 推荐方向提示 |
|---|---|---|
| 不吃香菜 | 完全避免香菜及相关调味 | 菜品和摆盘描述中不出现香菜，包括"香菜末"等配料 |
| 不吃葱姜蒜 | 完全避免葱、姜、蒜及其制品 | 包括蒜末、姜丝、葱花等隐藏配料也要排除 |
| 不吃辣 | 避免一切辣椒/花椒类调味 | 与"麻辣/微辣/酸辣"口味互斥，UI 上可互斥提示 |
| 无乳制品 | 避免牛奶、奶酪、黄油等 | 烘焙类需用替代品（植物奶、橄榄油）或排除 |
| 无麸质 | 避免小麦/大麦/黑麦及其制品 | 排除面粉、面条、面包，主食改用米饭/米粉/杂粮 |
| 素食 | 不含肉类、海鲜、禽类 | 蛋奶是否允许由备注框补充说明（纯素/蛋奶素） |

- 额外自由文本备注框（一句话，如"今天有点感冒想吃热乎的""对海鲜过敏"），与标签一起传给 AI，用于覆盖标签未能表达的个性化诉求

### 3.3 做法标签（含语义表）

预设做法标签（**多选**，因为一顿饭可能有多道菜、每道菜做法不同）：

| 标签 | 语义说明 | AI 推荐方向提示 |
|---|---|---|
| 火锅 | 食材分开涮煮，配锅底和蘸料 | 适合想要丰富食材体验、多人或一人小火锅场景，清淡或麻辣场景均适用，暖胃，适合冷天；适合消耗多种食材 |
| 香煎 | 少油煎至两面金黄，锁住肉汁 | 适合肉类、豆腐类、煎蛋；西式口味；可配海盐黑胡椒或椒盐等其他调料 |
| 清蒸 | 原汁原味，保留营养和清淡口感 | 适合鱼类、蔬菜、蛋羹；清淡；底油低盐；适合生病食用 |
| 凉拌 | 生食或焯水后冷调味 | 适合夏天/快手凉菜，省去开火时间；口味清爽 |
| 炖煮 | 长时间小火慢炖 | 适合根茎类蔬菜、带骨肉类，汤汁浓郁；暖胃；适合天冷食用 |
| 烧烤 | 明火/烤箱炙烤，外焦里嫩 | 适合肉类和部分耐烤蔬菜 |
| 快炒 | 大火快速翻炒，锁住脆嫩口感 | 适合绿叶菜、嫩肉片等，出餐快；常见做法 |
| 烘焙 | 烤箱烘烤类 | 适合面点、甜品 |
| 不限 | 不指定做法 | 由 AI 根据食材、场景用户需求和历史饮食习惯自由发挥 |

### 3.4 饮食目标自然语言交互（沿用并保留原模块）
- 一个输入框，提示语："最近想达成什么饮食目标？比如：增肌 / 减脂 / 补充维生素A"
- 沿用原 `/api/parse-goal` 的设计思路，把自然语言目标解析为结构化提示词片段，传给推荐生成接口（不强制展示解析结果给用户，作为内部增强）

### 3.5 AI 推荐生成（自己做）
- 综合输入：选中食材 + **是否仅用已有食材** + 口味/忌口（含语义表） + 做法标签（含语义表） + **份量与场景选择** + 自然语言目标 + （若已有）用户饮食习惯文档摘要（见 3.9）
- **份量与场景选择**（新增，解决"一顿饭可能不止一道菜"，且数量可以手动选）：
  - 场景化预设（单选 chip，每个自带语义，写入 prompt）：

    | 预设 | 语义说明 |
    |---|---|
    | 1人食 · 盖饭 | 一道主菜+米饭打底做成盖饭形式，1人份，操作简单 |
    | 1人食 · 小火锅 | 单人迷你火锅，少量食材+锅底，强调便捷和暖意 |
    | 1人食 · 1菜1汤 | 一道主菜+一道汤，简单不将就 |
    | 家常 · 2菜1汤 | 经典家庭餐桌组合，2道炒菜+1道汤 |
    | 丰盛 · 3菜以上 | 3~4道菜（至少含1荤1素1汤），适合聚餐/犒劳自己 |
    | 自定义 | 用户手动指定道数 |

  - 选"自定义"时出现道数 stepper（1~6），以及独立开关 **"+ 加甜品"**（任何预设下都可勾选，要求 AI 额外加一道甜品/餐后小食）
  - 做法标签和份量/场景选择解耦：做法标签描述每道菜的烹饪手法偏好，份量/场景决定生成几道菜、什么基本结构
- 输出结构（一次推荐 = 一顿饭，包含 1~N 道菜）：
  - 整顿饭的搭配名/简短小标题（如"今晚的家常搭配"）
  - 菜品列表，每道菜含：菜名、角色标签（主菜/主食/汤/甜品/小菜）、口味标签、所需食材清单（**每个食材标注 `fromPantry: true/false`**，`false` 表示用户没有、AI 新增建议购买的）
  - **购物清单**（仅当"仅使用已有食材"关闭且 AI 确实新增了食材时才非空）：把所有菜里 `fromPantry: false` 的食材去重汇总成一份清单，单独展示
  - 一段**统一的治愈系文案**：针对整顿饭的搭配逻辑给出正反馈和鼓励（不逐道菜分别写，避免啰嗦）
- 操作：
  - "就吃这桌 ✅" → 弹出"记到哪一餐"（早/午/晚/加餐 + 日期默认今天，可改）→ 整顿饭（含所有菜）写入同一条饮食记录，`channel: "自己做"`
  - "换一桌 🔄" → 基于同样输入整体重新生成
  - 文本反馈框："不想要香菜" "汤换成别的" 等 → 带着反馈重新生成整顿饭（沿用原 replan 逻辑）

### 3.5a 外卖推荐（新增）
- 简化输入：口味/忌口标签 + 自由备注 + 自然语言目标（不需要食材/做法/份量，因为不是自己做）
- AI 从"外卖库"中按用户口味/忌口/目标 + 用户饮食习惯文档（若有）匹配推荐 1~3 个外卖选项
- **外卖库数据来源（已确认）**：暂不接入真实外卖平台 API，AI 推荐时直接在本地 mock 数据库（结构见 §5 `TakeoutDish`，内置 10~20 条示例数据）中挑选匹配项，**后续由你手动补充/替换为真实数据**
- 输出结构（区别于"自己做"，不需要食材清单，去掉"角色"分类）：商家名、菜品名、品类、预估价位区间（可选）、推荐理由（治愈系文案，解释为什么这个外卖适合用户此刻的目标/心情）、适合搭配的小建议（如"配一杯热饮"）
- 操作：同样可"就吃这个 ✅"记录为一条 `MealRecord`，`channel: "外卖"`，`dishes` 仍按 Dish 结构记录（食材字段可留空或填"未知，外卖来源"）

### 3.5b 菜单库的品类（新增：固定大类 + 重新整理）
- **固定大类**：盖浇饭 / 面食 / 粉面米线 / 麻辣烫·香锅 / 火锅 / 烧烤炸物 / 家常炒菜 / 轻食沙拉 / 快餐简餐 / 粥品 / 小吃 / 汤 / 甜品饮品 / 其他（`app/lib/takeoutCategories.ts`）
  - 导入（截图/文字）、手动添加、编辑菜品都只认这一套；AI 拿不准时的出口是「其他」，**不许默认塞"快餐"**
  - 库里写的任何近义名字（"快餐类""米线""日式简餐"…）都会由 `canonicalCategory()` 收敛到这套大类上
- **重新整理分类**（菜单库页）：把库里已有的菜交给 AI 重判一遍品类 —— 只算不写，先把"改动清单 + 汇总（旧类→新类 N 道）"给用户看，点「应用」才写库，写前存快照因此可撤销
- 只改 `category` 字段，菜名/商家/价格/口味/忌口一律不动；分批请求（40 道/批），任一批失败则整体不写库，模型漏答或编造的 id 一律忽略

### 3.5c 菜单库导出（新增）
- 两种格式，用途不同（`app/lib/takeoutExport.ts`，纯字符串转换，可复制也可下载文件）：
  - **文字版（Markdown 清单）**：`# 我的食堂/外卖菜单库` + 统计行 + 一段"给 AI 的说明"（说明字段含义、并要求"只根据这份清单推荐，不要编造"），然后按**商家**分段、每道菜一行「- 菜名 ¥价格 ｜ 品类 ｜ 口味：… ｜ 忌口冲突：…」（空字段省略）。给 AI 阅读最省 token、最不容易误读；同时这个形态就是本页「文字导入」能吃的输入，可在另一台设备上重建菜单库。
  - **JSON**：自描述文档（`format/version/exportedAt/count/restaurants/categories/note/dishes`），`dishes` 保留 `restaurant/name/category/priceRange/flavorTags/avoidConflicts`，**不导出 id**（导入时按"商家+菜名"重新生成）。
- 不做 CSV：多值标签（口味/忌口）用逗号分隔会被引号与分隔符搅乱，AI 也更容易读错。

### 3.6 每周饮食回顾（替代原 dashboard 的营养量化记录）
- 周选择器：上一周 / 本周 / 下一周
- **Timetable 视图**：横轴为周一～周日，纵轴为时间段（早餐 / 午餐 / 晚餐 / 加餐），每个格子展示当次记录的（主）菜名 + 来源小图标（自己做/外卖）；若一餐含多道菜，显示"菜名 +N道"角标；点击格子可查看详情（完整菜品列表、各自食材/口味、AI 当时的推荐文案）
- 空格子可以"+"快速补录一餐（手动填菜名+食材，可一次填多道菜，不强制走 AI 流程；**也可以直接从「我的食堂/外卖库」点菜**——按菜名/商家搜索、按商家分组点选、**并能按品类筛**，选中的菜会带着口味标签进入这一餐并把来源置为"外卖"）
- **AI 营养分析师反馈区**：点击"生成本周分析"，AI 基于本周所有饮食记录（菜名+食材+口味+来源+用户饮食习惯文档）给出一段个性化点评和建议

### 3.7 手动编辑菜品（新增，饮食回顾页）
- 现实情况：用户不一定按 AI 生成的内容实际吃，需要支持事后修改
- 在 timetable 详情弹窗里，除查看外增加"编辑"按钮，编辑态下可：
  - 修改这顿饭里任意一道菜的菜名/角色/食材
  - 删除某道菜、手动新增一道菜（或"从菜单库加菜"——见 §3.6，编辑态默认收起该入口）
  - 整体删除这条 `MealRecord`
- 保存后该菜的 `source` 标记为 `"ai-edited"`（区分"AI推荐原样吃了"`ai`和"用户做了调整"`ai-edited`，纯手动新增的记录仍是 `manual`）—— 这个区分对 AI 营养分析师和饮食习惯文档很有参考价值，说明用户实际没有照搬推荐，反映了更真实的偏好
- 编辑不限制时间范围，所有历史记录都可编辑/删除（含跨天补录修改）

### 3.8 设置（沿用并中文化）
- API Key 配置面板（OpenAI Key），存储在 localStorage，留空则用服务端 `.env.local`
- 新增：**我的饮食笔记**入口，展示 3.9 中 AI 维护的用户饮食习惯文档全文，支持用户直接查看/手动编辑（透明化、可纠偏）

### 3.9 用户饮食习惯文档（新增）
- 系统额外维护一份"用户饮食习惯"文档，本质是一段持续被 AI 更新的 **Markdown 纯文本**，相当于一个不断进化的"用户饮食画像/笔记"
- 存储：MVP 阶段存 localStorage（key `recipe.userProfile.v1`），值为 markdown 字符串 + 更新时间戳
- 内容大致包含：常吃食材偏好、口味偏好趋势、忌口/过敏提醒、最近的饮食目标、AI 观察到的习惯变化（如"最近一周外卖比例上升""周末更偏好丰盛搭配"）
- 更新时机（已确认）：**仅**在用户于本周回顾页点击"生成本周分析"时，随该操作一并调用一次 `/api/update-profile`（不在每次确认一餐时触发，减少 API 调用和费用）
  - 触发时把最近一段时间的 `MealRecord` + 当前已有的饮食习惯文档一起发给 AI，AI 输出**更新后的完整 markdown 文本**，覆盖保存（而不是简单追加，避免文档无限膨胀）
- 用途：作为额外上下文注入 `/api/recommend`、`/api/takeout-recommend`、`/api/weekly-insight` 的 prompt，让推荐和分析更"懂用户"，不需要每次从零总结

- 精确营养量化（kcal/蛋白质/碳水/脂肪逐项计算）—— `/api/macros`、`/api/nutrition` 整体下线

## 5. 数据结构设计

```ts
// 常用食材标签
type CommonIngredient = {
  id: string;
  label: string;       // 用户输入的食材名，如 "鸡胸肉"
  createdAt: number;
};

// 一道菜里的一种食材
type DishIngredient = {
  label: string;
  fromPantry: boolean; // true=来自用户已选食材/厨房常备，false=AI新增建议购买
};

// 一道具体的菜（一顿饭可能包含多道）
type Dish = {
  name: string;          // 菜名
  role: "主菜" | "主食" | "汤" | "甜品" | "小菜";
  ingredients: DishIngredient[]; // 食材清单
  flavorTags: string[];  // 这道菜的口味标签（AI 总结）
};

// 一条饮食记录 = 一顿饭，包含 1~N 道菜
// （核心：必须能按日期+时间聚合，供"本周回顾"和"AI营养分析师"使用）
type MealRecord = {
  id: string;
  date: string;          // "2026-06-30" (本地日期)
  mealSlot: "早餐" | "午餐" | "晚餐" | "加餐";
  time?: string;         // 可选精确时间 "12:30"，timetable 主要按 mealSlot 分行
  title?: string;        // 这顿饭的搭配小标题，如"今晚的家常搭配"（单菜时可省略，直接用菜名）
  dishes: Dish[];        // 1~N 道菜
  channel: "自己做" | "外卖"; // 来源
  avoidTags: string[];   // 忌口标签（针对整顿饭）
  methodTags: string[];  // 做法标签（多选，外卖来源时可为空）
  portionPreset?: "1人食-盖饭" | "1人食-小火锅" | "1人食-1菜1汤" | "家常-2菜1汤" | "丰盛" | "自定义"; // 生成时选择的份量/场景
  dishCount?: number;     // 自定义份量时的手动指定道数
  onlyPantry?: boolean;   // 生成时是否勾选了"仅使用已有食材"
  shoppingList?: string[]; // 需购买的新增食材（去重汇总，onlyPantry=true 时应为空）
  goal?: string;          // 生成时的自然语言目标
  aiMessage?: string;     // AI 当时针对整顿饭的治愈系推荐文案（存档，回看详情用）
  source: "ai" | "manual" | "ai-edited"; // AI 推荐生成 / 手动补录 / AI推荐但用户编辑过
  createdAt: number;
};

// 本周分析结果（可选缓存，避免重复调用）
type WeeklyInsight = {
  weekStart: string;   // 周一日期
  reply: string;       // AI 营养分析师的反馈文本
  generatedAt: number;
};

// 外卖库中的一条菜品（MVP 阶段为本地 mock 数据，待替换为真实数据源）
type TakeoutDish = {
  id: string;
  restaurant: string;       // 商家名（示例数据）
  name: string;             // 菜品名
  category: string;         // 品类：**固定大类之一**（见 3.5b），如"麻辣烫·香锅" "盖浇饭" "轻食沙拉"
  priceRange?: string;      // 如 "¥20-30"
  flavorTags: string[];     // 对应 3.2 口味标签语义
  avoidConflicts: string[]; // 与哪些忌口标签冲突，用于推荐时过滤
};

// 用户饮食习惯文档（AI 持续维护的 markdown 文本）
type UserProfile = {
  content: string;   // markdown 正文
  updatedAt: number;
};
```

## 7.3 视觉风格规范（治愈系 / 橙黄浅蓝主题）

- 背景：暖米黄色 `#FFF8E7`（替代原来的纯白/浅灰）
- 强调色 A（食材/做法相关、悬浮装饰）：橙黄 `#FAC775` 系
- 选中态 chip（食材/口味/做法标签被选中）：浅橙黄背景 `#FCE8C8` + 深橙文字 `#6B4308`（背景调浅以保证文字对比度清楚）
- 强调色 B（积极反馈、确认类操作、AI 营养师消息气泡、本周回顾相关）：浅蓝 `#85B7EB` 系
  - 按钮/气泡背景用浅蓝 `#DCEFFC`，文字用深蓝 `#0C447C`
- 圆角：卡片 18px，按钮/标签统一用胶囊形（`border-radius: 999px`），整体比原版更圆润柔和
- 装饰元素：卡片角落点缀简单的圆形/叶子形状色块（橙黄+浅蓝，低饱和度、半透明），营造"治愈插画"氛围，但不喧宾夺主
- AI 文案气泡：使用衬线字体（serif）+ 心形图标，强调"温暖话语"的阅读体验，与普通 UI 文本区分开
- 深色模式：所有自定义色块需提供 `prefers-color-scheme: dark` 对应的深色版本（暖色调降低明度，而非直接反色）

## 8. 待确认问题

1. **做法标签**单选还是多选？PRD 暂定多选（因为一顿饭可能有多道菜、每道菜做法不同），可调整
2. **每餐记录是否限制一条**？比如同一天午餐已经记过一次，再生成一次推荐并"就吃这桌"，是覆盖还是允许同一时段多条记录（一条记录内部已经是多道菜了，原则上一个 mealSlot 当天对应一条 MealRecord 即可，但仍允许同一 mealSlot 多条，方便"正餐+加餐都算午餐后的加餐"等场景）？暂定：同一 mealSlot 当天允许多条 MealRecord，timetable 格子里多条时纵向堆叠展示
3. **常用食材标签**要不要支持"分类"（如肉类/蔬菜/主食）方便管理？MVP 先不做分类，纯平铺
4. **AI 营养分析师反馈**是否需要缓存（避免每次打开页面都重新调用 API 产生费用）？建议：按周缓存，同一周内点"刷新分析"才重新生成
5. 原项目的"忌口"目前设计为标签形式，是否需要也支持自由文本一起传给 AI（如"对海鲜过敏"）？建议在备注框里直接写，AI prompt 里会读取
6. **份量选择"丰盛"具体是几道菜**？暂定 3~4 道（不含甜品），加甜品开关勾选后再 +1 道。AI 返回的实际道数允许 AI 根据食材数量酌情微调（食材不够丰富时不强行凑数），但这是否需要在 UI 上提示用户"实际生成了X道"？暂定：直接按 AI 实际返回的 dishes 数组渲染，不强行约束数量
7. **"换一桌"的反馈框**：如果反馈针对某一道具体的菜（如"汤换成别的"），目前设计是整顿饭一起重新生成。是否需要支持"只换某一道菜，其他保留"的精细化操作？MVP 阶段暂定不做，统一整顿重新生成（实现简单，AI prompt 里会保留未提及的菜，自然倾向少改动）
